cclaw architecture

How cclaw talks to Cursor

Every model request runs through the Cursor CLI binary, so work bills through your Cursor account and cclaw never handles a token. But one binary does five different jobs, and two of the five channels are not the CLI at all.

  • ACP: long-lived, bidirectional
  • CLI: one-shot spawn
  • Files: config on disk
  • Inbound: Cursor calls us
ACP

agent acp

One subprocess for the life of the session, speaking JSON-RPC 2.0 over stdin and stdout through @agentclientprotocol/sdk. All prompts, streamed replies and tool consent ride this. It is the only bidirectional channel: requestPermission arrives from Cursor and our resolver answers it.

  • src/acp/client.ts:92 — Bun.spawn([bin, "acp"])
  • src/acp/client.ts:292 — prompt()
CLI

status · about · models · help acp

Short-lived invocations that answer one question and exit: who is signed in, which plan, which models exist, whether acp is available on this build. These carry metadata only. No prompt ever goes out this way.

  • src/cursor.ts:69 — runCursor()
  • src/cursor.ts:103 — status --format json
  • src/cursor.ts:132 — about --format json
  • src/models.ts:59 — models
RAW

cclaw raw

A process handoff rather than a protocol. Cursor's own TUI takes the terminal, under a cclaw profile. This is the mode that shows a real context-window figure, because that figure comes from the statusline.

  • src/commands/raw.ts:109 — Bun.spawn([bin.path, …args])
FILES

cli-config.json · permissions.json · rules/

Not the CLI at all. cclaw writes Cursor's own config files directly and Cursor reads them. That is how the allowlist, the denylist and the standing goal are enforced. A profile is just CURSOR_CONFIG_DIR and CURSOR_DATA_DIR in the spawned process's environment, which is also why a running agent does not pick up a policy change.

  • src/policy/seed.ts · src/policy/templates.ts
  • src/goal.ts — rules/ for the standing goal
  • src/profile.ts:160 — env handoff
STATUS

cclaw statusline

The one channel Cursor initiates. cli-config.json registers statusLine.command as cclaw, and Cursor spawns it on every refresh with a JSON payload on stdin. Today it is the only place a real context-window figure reaches cclaw, which is why /compact has none to work with.

  • src/statusline.ts — the payload we parse

What follows from this

No network of our own
The only https:// in non-vendored code is the install-command string in src/cursor.ts:12. Every model request travels inside Cursor's process.
Policy is a file
cclaw never asks the CLI to apply an allowlist. It writes permissions.json and cli-config.json, and Cursor reads them on start. Enforcement is Cursor's; the consent prompts in the TUI are ours.
Context is Cursor's
Over ACP, cclaw sends only the latest message and Cursor keeps the thread. The protocol does define a usage_update event carrying {used, size, cost}, but this Cursor build never sends one, so the chat footer reads ctx unknown and /compact works around it by asking the model to summarise itself.
One other binary
security, for the macOS keychain, storing the per-profile API key cclaw then passes as CURSOR_API_KEY. Cursor's own web login lives in a global keychain slot cclaw does not touch, which is the limit of profile isolation.
